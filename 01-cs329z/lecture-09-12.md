
# 第 9 讲　优化（Optimization）


## 9.0 本讲定位

你的 Agent 系统搭好了，但效果不够好——成功率只有 60%，成本还很高。这一讲讲**怎么系统地优化 Agent**：什么时候该优化 prompt、什么时候该训练模型、用什么方法。


## 9.1 前置知识

第 2 讲的训练流水线（预训练→SFT→RL），第 5 讲的 DSPy。


## 9.2 核心概念：两条优化路线

优化 Agent 性能有两条根本不同的路线：**上下文优化**（不改模型权重，只改给模型看的内容）和**权重优化**（通过训练改变模型参数）。

| 维度 | 上下文优化 | 权重优化 |
| --- | --- | --- |
| 改什么 | Prompt、Few-shot 示例、工具描述 | 模型参数 |
| 成本 | 低——只需推理 | 高——需要训练 |
| 速度 | 分钟级迭代 | 小时/天级 |
| 持久性 | 每次推理都要带优化后的上下文 | 优化固化在模型中 |
| 适用 | 快速迭代、特定领域适配 | 需要根本性能力提升 |


## 9.3 上下文优化方法


### Bootstrap Few-shot

自动从历史成功案例中挑选最好的 few-shot 示例。原理：让模型在训练集上跑，收集成功的例子，用这些例子作为后续推理的示范。


### MIPROv2

DSPy 的进阶优化器，同时优化指令措辞和 few-shot 示例的选择。它用贝叶斯优化在「指令空间」中搜索，找到使验证集表现最好的指令-示例组合。


### TextGrad

把「文本当作可微分的变量」——用自然语言描述「梯度」（哪里需要改进），然后让 LLM 根据这个「梯度」修改 prompt。类比：反向传播，但梯度是自然语言。


### GEPA

反思式 prompt 进化：让 Agent 在任务上运行，分析失败案例，自动进化 prompt。ICLR 2026 论文证明，这种方法在某些任务上甚至能超过强化学习。


## 9.4 权重优化方法


### SFT on Agent Rollouts

收集 Agent 成功的执行轨迹（Trajectory），用这些轨迹做监督微调。模型学会模仿成功的行为模式。


### RL with PPO / GRPO

用强化学习优化 Agent 的长期策略。PPO（近端策略优化）是经典方法，GRPO（群体相对策略优化）是 DeepSeek 提出的更高效方法——不需要单独的价值网络，用组内相对排名作为优势估计。


## 9.5 课件要点：什么时候优化 Prompt，什么时候训练权重

- 先优化 Prompt——成本低、迭代快，能解决 80% 的问题。
- Prompt 优化到瓶颈后再考虑训练——需要训练数据、算力、训练基础设施。
- 训练解决的问题通常是「根本性能力不足」——比如模型不会某种推理模式，prompt 教不会。


## 9.6 指定阅读

- Agrawal et al.《GEPA》(ICLR 2026)——反思式 prompt 进化
- Opsahl-Ong et al.《MIPRO》(EMNLP 2024)——多阶段 prompt 优化
- Shao et al.《DeepSeekMath》(2024)——GRPO 算法


## 9.7 动手实验

**实验：用 DSPy 的 BootstrapFewShot 优化你的 RAG 系统**。步骤：①准备 20 条「问题→正确答案」的训练集；②定义 DSPy Signature 和 metric（答案正确率）；③运行 BootstrapFewShot 优化器；④对比优化前后在测试集上的准确率。


# 第 10 讲　Agent 数据（Data for Agentic Systems）


## 10.0 本讲定位

「垃圾进，垃圾出」——Agent 系统的质量上限由数据质量决定。这一讲讲 Agent 需要什么样的数据：轨迹数据、示范数据、反馈数据，以及怎么建立数据飞轮（Data Flywheel）让系统越用越好。


## 10.1 前置知识

第 9 讲的优化概念。


## 10.2 核心概念：Agent 需要的三种数据


### 轨迹数据（Traces）

Agent 执行任务的完整记录：每一步的推理、工具调用、观察结果。轨迹数据是调试和训练的基础——你可以从中发现「Agent 在哪一步走错了」。


### 示范数据（Demonstrations）

人类或强模型演示的「正确做法」。用于 SFT 训练——让模型模仿专家行为。


### 反馈数据（Feedback）

对 Agent 输出的评价：好/坏、打分、修改建议。用于 RL 训练或 prompt 优化。


## 10.3 核心概念：数据飞轮

数据飞轮是 Agent 系统持续改进的引擎：**用户使用→产生数据→分析数据→改进系统→更好的用户体验→更多用户→更多数据**。关键是建立自动化的数据收集和分析管线，而不是靠人工积累。


## 10.4 课件要点：数据选择

不是数据越多越好——课件强调**数据质量 > 数据数量**。选择策略：

- **信息最大化**：优先收集模型最容易出错的场景的数据。
- **过滤策略**：去除低质量轨迹（如模型碰巧做对但过程混乱的）。
- **小而精的 Benchmark**：LIMA 论文证明，1000 条精心挑选的数据可以媲美大规模数据集的效果。


## 10.5 指定阅读

- Shankar《Data Flywheels for LLM Applications》(2024)
- Yang et al.《SWE-smith》(NeurIPS 2025)——规模化 Agent 数据
- Zhou et al.《LIMA: Less Is More for Alignment》(NeurIPS 2023)


## 10.6 动手实验

**实验：为你的 Agent 建立数据收集管线**。步骤：①在 Agent 的 Harness 中加入日志记录（每次调用的输入、输出、工具调用、延迟、成本）；②实现一个简单的「成功/失败」标注机制；③每周分析日志，找出失败率最高的任务类型；④针对这些任务类型收集更多训练数据。


# 第 11 讲　Agent 评测基础（Evaluation Fundamentals & Benchmark Design）


## 11.0 本讲定位

「没有评测，就没有优化」——这是 Agent 工程的第一定律。但 Agent 评测比普通软件测试难得多：输出不唯一、过程比结果重要、同一系统跑两次结果可能不同。这一讲讲怎么科学地评测 Agent。


## 11.1 前置知识

第 1 讲的 Agent 概念。


## 11.2 核心概念：为什么 Agent 评测难

- **输出非唯一**：同一个任务有多种正确做法，不能用「标准答案」判对错。
- **过程重要**：结果对了但过程有安全问题（比如查了不该查的数据），也算失败。
- **概率性**：同一系统跑 10 次，成功 7 次——这算好还是坏？


## 11.3 核心概念：4-Tuple 评测框架

CS329Z 提出的核心框架：一次完整的 Agent 评测由四个要素组成——

| 要素 | 含义 | 设计要点 |
| --- | --- | --- |
| Request（请求） | 给 Agent 的任务描述 | 要真实——来自用户会做的事，不是教科书造句 |
| Environment（环境） | Agent 运行时的外部条件 | 要可复现——每次评测从相同的初始状态开始 |
| Stopping Criteria（停止条件） | 什么时候判定任务结束 | 明确——成功/失败/超时/步数上限 |
| Scorer（评分器） | 怎么判断成功还是失败 | 要客观——规则 > 模型 > 人工 |


## 11.4 课件要点：好 Benchmark 的性质

- **真实性**：任务来自真实场景，不是人为构造的玩具问题。
- **可复现性**：任何人跑同一个 benchmark 应该得到一致的结果。
- **区分度**：能区分不同水平的 Agent——太简单或太复杂都没有区分度。
- **抗污染**：任务不应出现在模型的训练数据中。


## 11.5 指定阅读

- Zhu et al.《Establishing Best Practices for Building Rigorous Agentic Benchmarks》(2025)
- Polo et al.《tinyBenchmarks》(ICML 2024)——用更少样本评测


## 11.6 动手实验

**实验：为你的 Agent 写 10 条评测任务**。步骤：①选 10 个真实任务（3 简单 + 4 中等 + 3 对抗）；②为每条任务写清 4-Tuple（请求、环境、停止条件、评分器）；③实现自动评分脚本；④跑你的 Agent，记录成功率。


# 第 12 讲　LLM-as-Judge 与评测基础设施


## 12.0 本讲定位

第 11 讲讲了评测框架，这一讲深入评测的具体实现：当输出是开放式文本时，怎么自动判分？答案是**用另一个 LLM 当裁判**——但裁判本身也有偏见，需要先校准。


## 12.1 前置知识

第 11 讲的 4-Tuple 框架。


## 12.2 核心概念：三种评分器

| 评分器类型 | 原理 | 优势 | 劣势 |
| --- | --- | --- | --- |
| 规则评分器 | 代码断言（assert） | 确定、免费、快速 | 只能判结构化输出 |
| 模型评分器（LLM-as-Judge） | 另一个 LLM 打分 | 能判开放式输出 | 有偏见、有成本 |
| 人工评分 | 人看结果打分 | 最准确 | 最贵、最慢、不可规模化 |


## 12.3 核心概念：LLM-as-Judge 的偏见与校准

LLM 裁判有三种已被充分研究的偏见：

- **位置偏见**：偏爱先出现的答案。对策：交换顺序评两次取平均。
- **冗长偏见**：偏爱更长的回答。对策：评分标准中显式写明「冗余扣分」。
- **自我偏好**：偏爱与自己同族模型的输出。对策：裁判和被评模型用不同家族。


## 12.4 核心概念：pass@k 与 pass^k

Agent 是概率系统，「跑一次成功」什么都说明不了。两个互补指标：

- **pass@k**：采样 k 次，至少成功一次的概率。衡量系统的上限能力——「多试几次能不能行」。
- **pass^k**：采样 k 次，全部成功的概率。衡量系统的可靠性——「敢不敢无人值守上线」。

工程含义：pass@1=60% 的系统配自动重试，pass@5 可能接近 100%；但 pass^1=60% 意味着无人值守跑 10 个任务会坏 4 个。**产品能不能自治，看 pass^k**。


## 12.5 指定阅读

- Grace et al.《Demystifying Evals for AI Agents》(Anthropic, 2026)
- Zheng et al.《Judging LLM-as-a-Judge》(NeurIPS 2023)——偏见研究经典
- Ryan et al.《AutoMetrics》(ICLR 2026)——自动生成评估器


## 12.6 动手实验

**实验：量化你的裁判的位置偏见**。步骤：①准备 10 对答案（一好一差）；②以「好在前」和「差在前」两种顺序各让 LLM 裁判评一次；③统计位置偏见率（裁判偏爱先出现答案的比例）；④如果超过 60%，你的裁判需要校准。
