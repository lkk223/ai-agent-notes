# 第 1 讲　什么是 Agentic 系统？（Foundations & Landscape）


## 1.0 本讲定位

这是全课的第一讲，回答三个最根本的问题：**Agent 和普通聊天机器人有什么区别？Agent 系统由哪些部件组成？为什么现在需要专门研究 Agent？**后续所有讲次都是在这一讲的框架上往深处走。


## 1.1 前置知识

零门槛。你只需要知道「大语言模型（LLM）是一种能根据输入文字生成输出文字的 AI 系统」就够了。


## 1.2 核心概念：从聊天到做事

想象两个场景。场景 A：你问 ChatGPT「帮我写一封请假邮件」，它生成一段文字，你把文字复制到邮箱里自己发。场景 B：你告诉一个 AI 系统「帮我给老板发请假邮件，明天一天」，它自己打开邮箱、填写收件人、写入内容、点击发送，然后告诉你「已发送」。

场景 A 是**普通 LLM 调用**——模型生成文字，人来执行。场景 B 是 **Agent**——模型生成的不只是文字，而是**动作**（action），动作改变外部环境（邮箱的状态从「未发送」变成「已发送」），环境的新状态再反馈给模型，模型决定下一步。这个「动作→环境变化→反馈→再决策」的循环，就是 Agent 与普通 LLM 的本质区别。


### Agent 的五大部件

CS329Z 第一讲给出了 Agent 系统的解剖图——五个核心部件：

| 部件 | 作用 | 类比 |
| --- | --- | --- |
| LLM 核心（LLM Core） | 负责理解、推理、生成决策 | 大脑 |
| 推理（Reasoning） | 把大任务拆解成小步骤 | 大脑的思考过程 |
| 记忆（Memory） | 记住之前做过什么、用户偏好 | 笔记本 |
| 工具（Tools） | 能调用的外部能力（搜索、发邮件、读写文件） | 手 |
| 环境（Environment） | Agent 所处的外部世界（网页、代码仓库、操作系统） | 工作场所 |

这五个部件不是孤立的。LLM 核心负责决策，但决策的质量取决于推理过程是否清晰、记忆是否完整、工具是否好用、环境信息是否准确。**Agent 是一个系统，不只是一个模型**——这是全课反复强调的核心观点。


## 1.3 课件要点：Compound AI 系统

课件引用了 Berkeley BAIR 实验室的重要文章《The Shift from Models to Compound AI Systems》，核心观点是：**AI 的竞争力正在从「谁的模型更大」转向「谁的系统设计更好」**。

Compound AI 系统 = 多个组件（模型、检索器、工具、验证器）组合而成的系统。比如一个「写论文助手」可能包含：一个检索组件（查文献）、一个 LLM 组件（写综述）、一个验证组件（检查引用格式）。每个组件可以独立优化，系统的整体表现取决于组件之间的协作方式。


### Workflow vs Agent

课件特别区分了两个容易混淆的概念：**Workflow（工作流）**是预先写死步骤的流程——先检索、再总结、再发邮件，每一步由程序规则决定；**Agent** 是模型根据当前状态自己决定下一步做什么。

| 维度 | Workflow | Agent |
| --- | --- | --- |
| 谁决定下一步 | 程序员预先写死 | 模型根据环境反馈决定 |
| 灵活性 | 低——只能处理预设路径 | 高——能应对意外情况 |
| 可预测性 | 高——每次执行路径固定 | 低——同样输入可能走不同路径 |
| 适用场景 | 流程明确的重复性任务 | 需要开放式判断的复杂任务 |

> 💡 **讲师批注**：讲师批注：实际项目中，最好的方案往往是混合的——用 Workflow 控制大框架（保证可预测），在框架的某些节点里嵌入 Agent（处理开放式子任务）。比如「邮件分类」用 Workflow（规则明确），「起草回复」用 Agent（需要理解上下文灵活生成）。


## 1.4 课件要点：Agent 的四大挑战

课件列出了 Agent 系统面临的四个核心挑战，这四个挑战对应了课程后半段的四大主题：

- **可靠性（Reliability）**：Agent 是多步系统，每一步的小错误会累积放大。90% 的单步准确率意味着 10 步后只剩 35% 的整体成功率。
- **训练（Training）**：怎么让模型学会更好的 Agent 行为？需要什么样的数据和训练方法？
- **安全（Safety）**：Agent 能执行真实动作，错误动作的代价远大于错误文字。
- **评测（Evaluation）**：怎么判断一个 Agent「好不好」？单次成功不代表可靠，需要统计意义上的评测。


## 1.5 指定阅读

- Zaharia et al.《The Shift from Models to Compound AI Systems》(BAIR Blog, 2024)——Compound AI 系统的开山之作
- Weng《LLM Powered Autonomous Agents》(Lil'Log, 2023)——Agent 部件拆解的经典博客
- Kapoor et al.《AI Agents That Matter》(TMLR, 2025)——Agent 评测的系统性思考


## 1.6 动手实验

**实验：画出你的第一个 Agent 系统图**。选一个你熟悉的场景（比如「自动回复邮件」「自动整理桌面文件」），画出五大部件：LLM 核心负责什么决策？需要哪些工具？环境是什么？记忆存什么？推理过程大概几步？画完后标注：哪些步骤适合 Workflow（规则明确），哪些适合 Agent（需要灵活判断）。


# 第 2 讲　给 Agent 建造者的 LLM 原理（LLMs for Builders）


## 2.0 本讲定位

第 1 讲告诉你 Agent 是什么，这一讲回答「驱动 Agent 的大语言模型内部是怎么工作的」。你不需要会训练模型，但需要理解模型的能力边界——知道它为什么有时犯错、为什么有字数上限、为什么同样的输入会产生不同的输出。


## 2.1 前置知识

知道什么是「概率」即可。不需要线性代数或微积分。


## 2.2 核心概念：LLM 是怎么「思考」的


### Token：模型的「字母表」

LLM 不是以「字」或「词」为单位处理文字的，而是以 **Token** 为单位。一个 Token 大约等于英文的 0.75 个单词，或中文的 0.5–1 个汉字。模型看到的输入是一串 Token 编号（比如 [1523, 892, 4471...]），输出的也是一串 Token 编号。


### 下一个 Token 预测：模型的本质工作

LLM 的本质工作只有一件事：**给定前面所有 Token，预测下一个 Token 是什么**。它输出的是一个概率分布——比如「今天天气很」后面，「好」的概率 0.7，「冷」的概率 0.15，「热」的概率 0.08……然后按某种策略选一个。

这个简单的机制产生了惊人的能力：因为训练数据包含了人类几乎所有的文字，模型在「预测下一个 Token」的过程中学会了语法、事实、推理、甚至代码。


### 解码策略：怎么从概率分布中选 Token

模型每次给出的是概率分布，但我们需要选出一个具体的 Token。选择策略叫**解码（Decoding）**：

| 策略 | 做法 | 效果 | 适用场景 |
| --- | --- | --- | --- |
| 贪心（Greedy） | 永远选概率最高的 | 输出最确定但可能单调 | 需要精确格式的场景 |
| 温度（Temperature） | 温度高→更随机，温度低→更确定 | T=0 接近贪心，T=1 完全按概率 | 创意写作用高 T，代码用低 T |
| Top-p（核采样） | 只在累计概率前 p% 的候选中选 | 兼顾质量与多样性 | 通用场景 |

> 💡 **讲师批注**：讲师批注：Agent 系统通常用低温度（T=0 或 T=0.1），因为 Agent 需要精确的工具调用格式，随机性会导致 JSON 格式错误。这就是为什么「同一个 Agent 任务跑 10 次结果不同」——即使 T=0，模型的浮点运算也有微小不确定性。


### Transformer 注意力机制（简述）

Transformer 是 LLM 的底层架构。它的核心创新是**自注意力（Self-Attention）**：处理每个 Token 时，模型会「回头看」前面所有 Token，计算每个前面的 Token 与当前 Token 的相关程度（注意力权重），然后按权重加权汇总信息。

这让模型能捕捉长距离依赖——比如「这个变量在前面第 50 行定义过」。但注意力机制的计算量随序列长度平方增长，这就是**上下文窗口（Context Window）**有上限的原因。


### 上下文窗口与上下文工程

上下文窗口是模型一次能看到的最大 Token 数。2026 年主流模型的上下文窗口在 128K–1M Token 之间。但「能塞下」不等于「能处理好」——研究表明，模型对长上下文中部的信息利用率显著低于开头和结尾（Lost in the Middle 现象）。

**上下文工程（Context Engineering）**就是解决「给模型看什么、怎么看」的工程学问：哪些信息放进上下文、放在什么位置、什么时候压缩历史、什么时候检索外部知识。这是 Agent 系统的核心竞争力之一。


### 结构化输出与约束解码

Agent 需要模型输出精确的 JSON（工具调用格式），但模型本质上是在做「下一个 Token 预测」，没有内置的 JSON 合法性保证。**约束解码（Constrained Decoding）**通过语法规则强制模型只能生成合法 JSON——在每一步预测时，把不符合语法的 Token 概率设为零。


## 2.3 课件要点：预训练到后训练的流水线

一个 LLM 从「什么都不懂」到「能当 Agent 的大脑」，经历三个阶段：

- **预训练（Pretraining）**：在海量文本上做「下一个 Token 预测」，学会语言和世界知识。这是最贵的阶段（数百万美元）。
- **监督微调（SFT）**：用人工标注的「正确回答」训练模型学会对话格式、指令遵循、工具调用格式。
- **强化学习（RL）**：根据奖励信号（人类偏好或任务成功率）进一步优化行为。


## 2.4 指定阅读

- Vaswani et al.《Attention Is All You Need》(NeurIPS 2017)——Transformer 原始论文
- Katharopoulos et al.《Transformers are RNNs》(ICML 2020)——线性注意力，解决长序列效率问题
- Rajasekaran et al.《Effective Context Engineering for AI Agents》(Anthropic, 2025)——上下文工程实践指南


## 2.5 动手实验

**实验：感受温度对 Agent 输出的影响**。用同一个工具调用 prompt，分别以 T=0、T=0.5、T=1.0 各调用 5 次模型，记录每次输出的 JSON 格式是否合法、内容是否一致。你会发现 T=0 时格式几乎总是合法，T=1.0 时格式错误率显著上升。这个实验让你直观理解为什么 Agent 系统要用低温度。


# 第 3 讲　检索增强生成 RAG（Building Blocks）


## 3.0 本讲定位

LLM 有一个致命弱点：**它只知道训练数据里的信息**。你问它「我们公司上季度的销售额是多少」，它不可能知道——因为这个信息不在训练数据里。RAG（Retrieval-Augmented Generation，检索增强生成）就是解决这个问题的核心技术：**先从数据库里检索相关资料，再把资料塞进上下文让模型基于资料回答**。


## 3.1 前置知识

第 2 讲的 Token 和上下文窗口概念。


## 3.2 核心概念：为什么需要检索

想象你问一个博学的教授一个关于你公司内部文档的问题。教授虽然博学，但没看过你的文档。有两种解决方案：方案 A，把所有文档让教授背下来（对应「微调模型」，成本高、更新慢）；方案 B，把相关文档递给教授，让他看了再回答（对应 RAG，灵活、实时、成本低）。

RAG 就是方案 B。它的完整流程分两步：**索引阶段**（离线，把文档切碎、编码、存进数据库）和**查询阶段**（在线，用户提问→检索相关文档片段→塞进 prompt→模型生成回答）。


### 索引阶段：把文档变成可检索的形式

**第一步：切块（Chunking）**。把长文档切成小片段（通常 200–500 Token）。太大——检索不精准且浪费上下文空间；太小——片段缺乏上下文，模型看不懂。

**第二步：编码（Embedding）**。把每个文本片段通过编码模型转换成一个向量（一串数字，比如 1536 维）。语义相近的文本，向量距离也相近。

**第三步：存入向量数据库**。把所有片段的向量存入专门的向量数据库（支持高效的「找最近邻」查询）。常用技术包括 HNSW（分层可导航小世界图），一种高效的近似最近邻搜索算法。


### 查询阶段：检索与生成

用户提问后，系统做三件事：**检索**（把问题也编码成向量，在数据库中找最相似的 K 个片段）、**组装**（把检索到的片段拼进 prompt，加上指令「请根据以下资料回答」）、**生成**（模型基于资料生成回答）。


## 3.3 课件要点：检索技术的演进


### 从关键词到语义：三代检索技术

| 技术 | 原理 | 优势 | 劣势 |
| --- | --- | --- | --- |
| BM25（关键词检索） | 统计词频和逆文档频率 | 精确匹配专业术语 | 不理解语义 |
| DPR（密集段落检索） | 神经网络编码语义向量 | 理解语义相似 | 可能漏掉精确术语 |
| 混合检索（Hybrid） | BM25 + 向量双路召回后融合 | 兼顾精确与语义 | 系统复杂度增加 |

CS329Z 推荐的工程实践是**混合检索**：同时用 BM25 和向量检索各召回一批结果，然后用融合算法（如倒数排名融合 RRF）合并排序。实验表明混合检索在大多数场景下优于单一路线。


### 进阶技术

- **重排序（Reranking）**：初步召回后用一个更精细的模型对结果重新排序，提高 Top-K 的质量。ColBERT 是一种高效的延迟交互重排序模型。
- **上下文检索（Contextual Retrieval）**：在切块时保留文档的上下文信息（如「这是第 3 章第 2 节的内容」），避免片段孤立。
- **RAPTOR**：对文档做层次化摘要——先切小块，再对小块聚类摘要，再对摘要聚类摘要，形成树状结构。查询时可以在不同层级检索。
- **Agentic RAG**：让 Agent 自己决定「什么时候检索、检索什么、检索几次」。Self-RAG 和 Search-R1 是这个方向的代表工作。


## 3.4 课件要点：RAG 常见失败模式

- **检索不到**：相关信息不在数据库中，或切块方式导致关键信息被切散。
- **检索不准**：召回了无关片段，干扰模型判断。
- **模型不看**：检索到了正确片段，但模型忽略了它（Lost in the Middle）。
- **模型幻觉**：模型不基于检索到的资料回答，而是编造信息。

> 💡 **讲师批注**：讲师批注：调试 RAG 系统时，先区分「检索问题」和「生成问题」。手动检查检索结果是否包含正确答案——如果包含了但模型没答对，是生成问题；如果没包含，是检索问题。两类问题的修法完全不同。


## 3.5 指定阅读

- Lewis et al.《Retrieval-Augmented Generation for Knowledge-Intensive NLP Tasks》(NeurIPS 2020)——RAG 原始论文
- Karpukhin et al.《Dense Passage Retrieval》(EMNLP 2020)——DPR 向量检索
- Khattab & Zaharia《ColBERT》(SIGIR 2020)——高效重排序


## 3.6 动手实验

**实验：从零搭一个最小 RAG 系统**。步骤：①准备 5 篇短文档（每篇 200 字左右）；②用 OpenAI Embedding API 或本地模型把每篇文档编码成向量；③写一个「余弦相似度」函数；④输入一个问题，计算它与每篇文档的相似度，取 Top-2；⑤把 Top-2 文档拼进 prompt，让模型回答。整个系统不超过 50 行 Python 代码。


# 第 4 讲　工具使用与函数调用（Tool Use & Function Calling）


## 4.0 本讲定位

第 1 讲说 Agent 有「手」（工具），这一讲深入讲解这双手是怎么工作的：**模型怎么知道有哪些工具可用？怎么决定调用哪个工具？调用结果怎么回到模型？**这是 Agent 从「会说」到「会做」的关键一跃。


## 4.1 前置知识

第 1 讲的 Agent 五大部件，第 2 讲的结构化输出。


## 4.2 核心概念：工具调用的完整链路

工具调用（Tool Calling）的完整过程可以拆成五步：

- **①工具注册**：开发者定义工具的名称、描述、参数格式（JSON Schema），告诉模型「你有哪些工具可用」。
- **②模型决策**：模型读取用户请求和工具列表，决定是否需要调用工具、调用哪个、传什么参数。
- **③生成调用**：模型输出一个结构化的工具调用请求（JSON 格式），包含工具名和参数。
- **④执行调用**：Harness（Agent 框架）解析 JSON，校验参数，在环境中执行工具，获得结果。
- **⑤结果回灌**：工具执行结果作为新的消息加入对话历史，模型读取结果后继续决策。


### 工具描述就是 Prompt

CS329Z 反复强调的一个核心洞察：**工具的名称和描述不是「文档」，而是「给模型看的指令」**。模型根据工具描述来决定「什么时候用哪个工具」——描述写得模糊，模型就会在该调用时不调用、不该调用时乱调用。

```python
# 坏的工具描述（模糊）
{"name": "search", "description": "搜索"}

# 好的工具描述（明确边界）
{"name": "search_web",
```

## 4.3 课件要点：工具调用的技术演进


### Toolformer：让模型自学用工具

Toolformer（Meta, 2023）是一项开创性工作：它证明了语言模型可以通过自监督学习学会**何时调用 API、调用哪个 API、传什么参数**。方法是在文本中插入 API 调用标注，让模型在预训练阶段就学会工具使用模式。


### Gorilla 与 ToolLLM：规模化工具调用

Gorilla（Berkeley, 2024）解决了「几千个 API 怎么选」的问题：通过检索增强的方式，先从 API 库中检索最相关的几个，再让模型在这几个候选中选择。ToolLLM 进一步构建了大规模工具调用训练数据集。


### MCP：模型上下文协议

MCP（Model Context Protocol）是 Anthropic 提出的开放协议，目标是**统一工具接入方式**——任何工具/数据源按 MCP 标准实现一次，任何支持 MCP 的 AI 客户端就能即插即用。类比：USB 接口统一了外设接入方式，MCP 统一了 AI 工具接入方式。

MCP 的核心概念：**MCP Server**（工具提供方，暴露工具列表和执行接口）、**MCP Client**（AI 应用方，发现工具并发起调用）。Server 和 Client 之间通过标准 JSON-RPC 协议通信。


## 4.4 课件要点：工具调用的评测

课件介绍了三个工具调用评测基准：**BFCL**（Berkeley Function Calling Leaderboard，评估函数调用的准确性）、**ToolBench**（大规模工具使用能力评测）、**τ-bench**（评估 Agent 在对话中使用工具完成任务的能力）。

## 4.6 动手实验

**实验：写一个最小的工具调用循环**。步骤：①定义两个工具（get_weather 和 calculate），各写清楚名称、描述、参数 Schema；②构造包含工具列表的 API 请求发给模型；③解析模型返回的 tool_call；④用 Python 函数模拟执行；⑤把结果作为 role=tool 的消息追加到对话；⑥再次请求模型，观察它是否基于工具结果生成最终回答。全程不用任何框架，只用 OpenAI API。
